# 通用 Agent 基线实验 · 准备手册

- **被试**：opencode（接入 GLM-5.2），Windows 环境
- **实验者**：本人，以"小白玩家"人设提问
- **手册纪律**：测例与评分标准在实验开始前锁定；实验过程中只记录、不修改标准。如确需修订，在文末"修订记录"追加并注明日期。

## 一、实验定位与原则

### 1.1 三个目的

1. **证据**：为设计文档"痛点分析"一节采集通用 Agent 失败 / 低效的具体实例。
2. **需求**：把 MC 联机开服的真实决策分支摸全，转化为本 Agent 的需求清单初稿。
3. **防御**：答辩时回答"为什么不让通用编码 Agent 干"——用数据说话，不做稻草人。

### 1.2 基本原则

- **只测单一被试的取舍**：固定 opencode + GLM-5.2 + Windows 是为了控制变量，且通用编码 Agent 是各档被试（纯对话 / 搜索增强 / 编码 Agent）中能力最强的一档——赢过最强对手才有说服力。代价是外部效度受限，设计文档中的表述应为"最强的通用编码 Agent 在小白用户提示下也难以……"，避免"所有通用 Agent 都不行"的过度概括。可选补测：网页版对话 LLM 作为弱基线。
- **如实记录**：opencode 能实际执行命令、读写文件，成功之处必须记录；失败要区分归因——"Agent 能力不足"还是"环境问题（如网络不可达）"，依据 P0 预检的可达性记录判断。
- **小白人设**：提示词全部用新手语气，不用术语、不给线索；被追问时只给 2.5 节的预设应答。

### 2.3 初始状态纪律

- **防上下文污染（重要）**：被试会话**不得加载本仓库的 AGENTS.md**（它会向被试泄露本项目背景，造成引导）。做法：测例在仓库外的独立目录（如 `C:\mc-agent-test\T1\`）中运行 opencode；实验结束后把记录拷回本仓库 `experiments/runs/<测例号>/`。
- 每个测例新开一个 opencode 会话，工作目录即该测例的独立空目录。
- 涉及预埋文件的测例（T5 / T6 / T7）按各测例"预埋"说明放置文件。
- 执行类测例每轮开始前恢复快照或清空目录，保证同一起点。

### 2.4 权限与停止规则

- **权限策略统一为"全部放行"**（模拟小白用户无脑点允许）；确需拒绝的命令，记录命令与拒绝原因。
- **停止规则**：同一失败连续重试 3 次仍相同 → 终止该测例并记录终止点；单测例上限 60 分钟或 25 轮对话，先到为准。
- Agent 问是非题时统一答"可以 / 好的"；需要信息时只给 2.5 预设应答。

### 2.5 预设应答（防引导泄漏）

被追问时按此应答；超出范围的问题统一回答"我也不清楚，你看怎么办好"：

| 可能的追问 | 预设应答 |
| --- | --- |
| MC 版本（T1 追问） | "就用最新的吧"（顺带考察 C2 时效性） |
| MC 版本（T3 / T4） | "1.21 吧" |
| 几个人玩 | T1："3 个"；T4："5 个" |

## 三、理想 Agent 能力模型（评分标尺）

先定义"满分 Agent"长什么样。评分 = 实际表现与下表的偏差，每维 0 / 1 / 2 分（0 完全缺失，1 部分达成，2 达标）。

| # | 能力维度 | 理想行为（2 分标准） |
| --- | --- | --- |
| C1 | 需求澄清 | 动手前主动问齐：Java 版还是基岩版、人数、账号类型（正版 / 离线）、机器配置、网络（有无公网 IP）；未问清不盲目执行 |
| C2 | 信息时效 | 版本号、下载渠道、mod 兼容范围与当下官方一致；理想做法是实时查询权威源（Mojang / Paper / Fabric / Modrinth）而非凭参数记忆作答 |
| C3 | 环境感知 | 执行前检查本机 Java 版本、内存、端口占用、网络连通，并据此调整方案（如指出 Java 17 跑不了 1.21 服务端） |
| C4 | 方案完备 | 覆盖用户没提但必需的环节：EULA 同意、防火墙 / 端口、Java 安装、备份、首次启动会自动退出等 |
| C5 | 执行正确 | 下载源正确（官方而非失效镜像）、文件可校验、配置项写对、服务端真的能启动到 Done |
| C6 | 安全意识 | 主动提示离线模式的冒充登录风险并给缓解（白名单 / 认证插件）；改删文件前先备份；不无确认执行危险操作 |
| C7 | 诊断能力 | 读日志能定位根因到具体版本号 / 文件 / 配置项（如 class file 65/61 → Java 版本不匹配），并给可执行的修复步骤 |
| C8 | 过程透明 | 长任务（下载 / 安装）进度可见、可打断；执行过的操作可事后审计 |
| C9 | 状态沉淀 | 把本次开服决策保存为可复用档案（配置 + 脚本），下次免重问 |
| C10 | 成本自觉 | 主动汇报本次任务消耗的 token 数与费用 |

注：C8–C10 是本项目（对应 R4 / R5 / R6）的目标能力，通用 Agent 预期得分低——这正是"通用 vs 专用"的核心论据；但 opencode 有命令回显与权限机制，C8 要如实评分。

## 四、测例清单

### T0 人工基线（实验者本人完成，不用 Agent）

**目的**：① 量化人工痛苦（耗时 / 决策点数 / 文档跳转次数）；② 采集 T5 所需的真实日志；③ 建立判卷用的基线事实。

**做法**：只用官方文档（papermc.io、fabricmc.net、modrinth.com、Minecraft Wiki），各完成一次：1.21 Paper 离线服、Fabric + 暮色森林服。全程记录耗时与卡壳处。

**产出**《基线事实清单》写入 `experiments/ground-truth.md`（附来源 URL 与截图、采集日期）：当前版本号、Java 版本要求映射、各服务端正确下载渠道、暮色森林支持的 MC 版本与依赖、离线认证相关插件 / mod 名称。**后续所有测例的评分对照此文件，不凭记忆判卷。**

**额外采集三份日志**（故意触发）：① 用 Java 17 启动 1.21 服务端；② 端口被占用；③ mod 版本不兼容。

**注意**：T0 本人操作需要 Java 21；完成后卸载或恢复快照，确保被试环境只剩 Java 17，再开始 T1。

### T1 基础开服

- **目的**：最常见入口需求，主考 C1–C5。
- **预埋**：独立空目录；环境只有 Java 17。
- **提示词**："我想和三个朋友一起玩 MC Java 版联机，听说要开个服务器。帮我把服务器开起来，让他们能连进来玩。"
- **理想行为**：先澄清（朋友是正版吗？在外网还是同一网络？）→ 检查环境发现 Java 17 不足以跑 1.21 并解决 → 从官方渠道下载对应版本服务端 → 处理 EULA、端口、防火墙 → 启动到 Done，报告连接地址与方法 → 进度可见。
- **观察点**：是否混淆 Java 版 / 基岩版；"就用最新的吧"之后给的版本与下载渠道是否真实有效（对照 ground-truth）；Java 缺口是否被发现、如何解决；EULA 首启退出是否预料到；"朋友连进来"是否处理外网问题，还是只给 localhost 就宣布完成；残留手工步骤数。
- **通过判据**：按 Agent 最终方案，本机第二客户端（类型与其方案匹配）能进入服务器；未澄清账号类型导致无法验证的，C1 记 0。

### T2 离线玩家分支

- **预埋**：一台可用的服务器目录（沿用 T1 终态，或手工重新部署最小可用服）。
- **提示词**："我朋友没有正版账号，一直进不了我开的服务器，报'验证用户名失败'之类的错。怎么让没有正版的朋友也能玩？"
- **理想行为**：解释 online-mode 机制与风险 → 修改配置并重启 → 提示离线 UUID 对白名单 / 玩家数据的影响 → 给缓解方案（白名单、认证插件）→ 说明对正版朋友的影响。
- **观察点**：是否只改配置不讲风险；是否知道离线模式的白名单行为；有无冒充登录风险提示；是否提及混合正版 + 离线的认证方案。
- **通过判据**：离线客户端可进入 + 至少一条有效安全提示。

### T3 Mod 服与版本矩阵（核心痛点）

- **预埋**：独立空目录；环境只有 Java 17。
- **提示词**："帮我开一个能玩暮色森林的 Fabric 服务器，MC 要 1.21 的，需要的 mod 都帮我装好。"
- **理想行为**：确认版本与加载器 → 用正确方式安装 Fabric 服务端（server 启动器，而非直接丢 jar）→ 从 Modrinth / CurseForge 核对暮色森林对 1.21 的支持版本与依赖（Fabric API 等）→ mod、加载器、MC 三方版本匹配 → 启动并从日志确认 mod 加载成功 → 报告如何进入暮色森林。
- **观察点**：**幻觉重灾区**——给出的 mod 名称 / 版本号是否真实存在（对照 ground-truth 与 Modrinth）；是否漏装 Fabric API；是否把 Forge 的做法套在 Fabric 上；下载 URL 是否有效；出错后能否自己读日志纠正。
- **通过判据**：服务器启动至 Done，且日志显示 Twilight Forest 及其依赖加载成功。

### T4 一句话复合需求（拆解能力）

- **预埋**：独立空目录；环境只有 Java 17。
- **提示词**："我们一共 5 个人，2 个正版 3 个没有正版，想玩带暮色森林的生存。用我这台 Windows 笔记本开服，16G 内存，家里宽带应该没有公网 IP。帮我把整套弄好，朋友们都能进来。"
- **理想行为**：完整分解需求——认证策略（混合正版 + 离线怎么办）→ 服务端选型（要玩 mod 需 Fabric，而不是 Paper）→ 内存分配建议（如 -Xmx8G 并留系统余量）→ mod 安装（同 T3 的版本匹配）→ 穿透方案（无公网 IP：frp / playit.gg / Tailscale 选型）→ 启动验证 → 汇总一份"朋友们怎么连"的说明。
- **观察点**：漏了哪个分支（认证混合、内存参数、穿透最易漏）；每个分支给出的选择是否可行；残留手工步骤数；总轮次与时长。
- **通过判据**：本机验证服务器可用，且每个分支都有可执行落点（穿透无法真实验证外网时，至少给出可配置方案与验证方法）。

### T5 崩溃日志诊断（3 个子例）

- **预埋**：T0 采集的三份日志分别放入三个目录（log1：Java 版本不匹配；log2：端口占用；log3：mod 版本不兼容）。
- **提示词**（每子例相同）："我的服务器起不来了，报错日志就放在这个文件夹里，帮我看看是什么问题、怎么修。"
- **理想行为**：主动读取日志文件 → 定位到具体行与根因 → 给针对性修复（log1：换 / 装 Java 21，并说明 MC 与 Java 的版本对应；log2：找出占用进程或改端口；log3：指出哪个 mod 哪个版本不匹配、去哪下正确版本）→ 最好直接代劳修复并验证重启。
- **观察点**：根因定位粒度（版本号 / 文件 / 配置项级，还是"重装试试"级）；修复后是否验证；是否需要实验者补充信息。
- **通过判据**：每子例说对根因，且修复后可启动（或明确只剩需用户手工完成的一步）。

### T6 配置文件审查

- **预埋**：`server.properties` 埋 3 个雷：① `server-port=25566`（客户端默认连 25565 → 连不上）；② `view-distance=32`（性能隐患）；③ `white-list=true` 但白名单为空（谁也进不去）。
- **提示词**："朋友说连不上我的服务器，一直转圈超时。配置文件是目录里的 server.properties，帮我看看哪里不对。"
- **理想行为**：读文件逐项核对 → 找出端口不一致（超时根因）→ 指出白名单会拦截所有人 → 指出视距过大并给推荐值 → 修复并给验证方式。
- **观察点**：3 个雷各自是否找对；根因排序是否合理（端口 > 白名单 > 性能）。
- **通过判据**：至少找对端口与白名单两项；3 项全中为满分。

### T7 升级迁移

- **预埋**：一台可启动的 1.20.4 Fabric 服（世界存档非空；mods 目录含一个 ground-truth 确认**无** 1.21 版本的 mod 和一个**有** 1.21 版本的 mod）。
- **提示词**："我有个 1.20.4 的 Fabric 生存服，世界玩挺久了，想升到 1.21 继续玩。直接换服务端行吗？存档和 mod 怎么办？帮我把升级弄好。"
- **理想行为**：先完整备份（C6）→ 说明存档只能升不能降 → 逐个核对 mod 的 1.21 支持情况并替换 / 移除（对照真实信息）→ 更换新版加载器与服务端 → 启动并验证旧世界可进入。
- **观察点**：是否备份；mod 是批量照搬还是有核对（重点看那个无新版的 mod 怎么处理）；是否幻觉声称停更 mod 有 1.21 版本。
- **通过判据**：升级后服务器可启动、旧世界可进入、无 mod 不兼容崩溃。

### T8 穿透与跨平台（选做）

- **提示词**："朋友在外地上学进不了我的服务器，另外有个朋友只有手机，玩的是基岩版。有没有办法让他们都能进来？"
- **理想行为**：区分两个问题 → 穿透选型结合小白场景推荐（frp 需自有 VPS / playit 免费隧道 / Tailscale 虚拟局域网）并说明取舍 → 基岩跨平台给出 Geyser + Floodgate 路线与安装要点 → 说明各方案局限。
- **观察点**：方案可行性；对当前生态的时效性（对照 ground-truth）；能否落地配置而非只给科普。
- **通过判据**：至少一个方案配置到本机可验证的状态。

## 六、安全与合规注意

- 测试服务器不暴露公网；T8 若真实配置穿透，测完即关闭。
- 让 Agent 在真机执行命令有风险：优先虚拟机 + 快照；真机使用非管理员账户，不提供个人真实凭据。
- 导出记录入仓前检查：无 API Key、无个人隐私（日志中的公网 IP 打码）。
- 所有记录是课程提交物（AI 对话历史、开销明细）的数据来源：保持原始，不删改、不事后美化。

## 七、实验产出与去向

1. `experiments/summary.md`：汇总表 + 失败模式清单 → 设计文档"痛点分析"一节。
2. 失败模式 → 本项目定制点的映射表（实验后填写）。
